# 已知失效模式与排障手册

> 整理时间：2026-10。来源：一次真实排障 + 一周运行观察。
> 用途：把「机器人看起来不想说话」的几种情况区分开 —— 它们表面症状几乎一样，根因和处置完全不同。
> 相关：[how-to-extend.md](how-to-extend.md)（分层与扩展）· [../qq-bridge/docs/guides/SECURITY_BASELINE.md](../qq-bridge/docs/guides/SECURITY_BASELINE.md)

## 一、先看这张表

| 症状 | 日志指纹 | 真实原因 | 处置 |
| --- | --- | --- | --- |
| 彻底不说话，也不报错 | `回合完成但无文本`，且会话事件里只有 `turn/start` → `turn/end blocked` | 会话被归档，被 archived-session-gate 拦在模型之前 | 取消归档；见 §2 |
| 某个会话每轮都报 400 | `agent 处理出错：<provider> request failed (400)`，重启 / 取消归档均无效 | 会话历史里有非法字符（孤立代理项） | 修历史或重置该会话；代码层用 `clipText`；见 §3 |
| 明明在问它，就是不接 | 无任何错误日志，只有 `会话繁忙，暂存` / `跳过补发` | 唤醒判定未命中，或忙期积压被未读水位判成「已处理」 | 见 §4 |
| 聊天里突然冒出系统话术 | 对端收到「已停止」这类提示 | 系统提示语走了发送通道 | 见 §5 |

判断顺序建议：**先看会话事件里有没有 `step/start`**。
有 → 模型跑过了，问题在「该不该说 / 说没发出去」；没有 → 卡在投递前（归档、限流、白名单），模型根本没跑。

## 二、会话被归档 → 回合全部 `blocked`

**指纹**

```text
bridge.log:  回合完成但无文本 (group:xxx)
会话事件:     turn/start → turn/end {"kind":"blocked"}      ← 中间没有 step/start
```

**根因**：DSH 会把「已归档会话」的投递挡在模型之前。桥接侧只能看到"回合结束但没产出"，于是记成「无文本」——看起来像机器人懒得说话，实际是它压根没被允许跑。

**触发方式**：在 DSH 的会话列表里归档该会话；或沿用了早期排障时的归档操作。**这是状态问题，不是代码 bug。**

**处置**

```bash
# 1) 确认（非空即异常；活跃会话不应出现在这里）
python3 - <<'PY'
import json, os
p = os.path.expanduser('~/.dsh/storages/workspace.json')
for ws in json.load(open(p))['tables']['workspaces'].values():
    print(ws.get('path'), ws.get('archivedSessionIds'))
PY

# 2) 取消归档（走 RPC，不要手改 workspace.json）
#    payload 形状为 { request: { sessionId } }
```

**预防**：清会话请用桥接的 `POST /api/session/reset`，不要用 GUI 的归档。
建议桥接在 `turn/end.reason.kind === 'blocked'` 时打明确警告，并在启动时校验映射会话是否被归档、自动解档。

## 三、历史含非法字符 → 该会话永久 400

**指纹**

```text
每轮都出现：agent 处理出错：… request failed (400)
特征：只影响某一个会话；私聊/其他群正常；连发一句 hello 也 400；
      重启、取消归档、保留上下文重试都无效。
```

**根因**：会话历史里的某条文本含**孤立代理项**（lone surrogate，即被切掉一半的 emoji，如 `\ud83d`）。它被序列化进请求体后不是合法 JSON，provider 解析失败返回 400；而这条消息已经在历史里，**之后每一轮都会带着它**。

**为什么难查**：provider 的错误体是 `{"detail": "..."}` 形状，而多数客户端只读 `error.message`，于是错误被降级成一句无信息的 `(400)`。真实内容类似：

```text
Failed to parse the request body as JSON:
messages[N].content[0].text: lone leading surrogate in hex escape
```

定位方法：按序列化规则**重建该会话的请求体**直接重放，即可拿到被吞掉的原文。

**常见成因**：按 UTF-16 码元截断消息文本（`str.slice(0, n)`）时正好切在 emoji 的两个码元中间。

**处置**

1. 修复历史里那个字符（把半个代理项补完整，或替换为 `�`）；
2. 若运行时已把该会话缓存在内存中，改磁盘文件不会生效 —— 需要**重置该会话**或重启运行时；
3. 代码层根治：所有"截断消息文本再喂模型"的地方改用**按码点截断**的 `clipText()`，并在提示词出口加一道**孤立代理项清洗**兜底。

**预防**：见 [how-to-extend.md](how-to-extend.md) 第七节第 1 条（硬约束）。

## 四、明明在问它却不接

三种互不相同的原因，症状都是"没反应"。

### 4.1 唤醒判定没命中

唤醒只认有限几种信号：被 @、消息引用了机器人自己的消息、提到昵称、命中关键词表、被判定为"直接提问/挑战"、指定成员发言、按概率随机。

其中"提问"是**正则判定**：既要有 AI 相关词（或出现"你/您"），又要带疑问/比较语气。实践中的漏判：

- 用称谓而不用"你"：`叔叔也玩这个吗`、`老哥在不在`
- 用指代而不用名字：`这条鱼今天怎么这么菜`、`它是不是傻`
- 表里没有的说法：`bot 今天怎么哑了`
- 只有图片 / 只有表情：文本为空，**根本不产生唤醒信号**

**自查**：把候选句丢进判定函数看是否命中；更实用的做法是**收集真实漏判样本**再补词表或改成打分。

**建议方向**：把"指向判定"从正则白名单换成打分（自称 / 称谓 / 代词 / 是否回复机器人 / 最近是否与机器人互动），并给"图片 + 近期互动"一个低优先级唤醒。

### 4.2 忙期积压被"已读"吞掉

```text
会话繁忙，暂存唤醒原因 …（pendingWakeKey）
…已被当前回合处理，跳过补发
```

机制：会话忙时新唤醒进入待发队列；回合结束后补发时，**用未读水位判断"这条是不是已处理"**。于是模型在一轮里读完全部未读、只回其中一条、再标记已读到最新水位，其余消息就被判为"已处理"而丢弃 —— **"被读过"被当成了"被回复过"**。

叠加两个放大因素：

- 待发队列**一次只补一条**，调用点只在回合结束时；
- 单回合可能很长（收尾前会做数分钟的"沉睡前观察"），积压消化速度低于产生速度。

**建议方向**：丢弃条件改成"该 seq 是否已产生过发送动作"；待发项加入过期时间（几分钟），避免 20 分钟后复活一条旧唤醒；补发放宽到"每回合最多 N 条"。

### 4.3 回复窗口只有一次

发完消息后通常排一次 `+30s` 的回复检查；这一轮若没有再发言就**不续期**。对方在 30 秒后追问，只能指望命中触发词或概率。

**建议方向**：回复检查支持有限次数退避续排（如 30s / 60s / 120s）。

### 4.4 未读数不等于漏回

回复后如果没走收尾动作（标记已读 / 重设唤醒），未读水位不会前进。排查时**不要用未读数判断"有没有漏回"**，要看：最后一条来信之后有没有 bot 的发送记录。

### 4.5 发送被限流 → 整个回合卡死

**指纹**：模型侧反复出现 `发送失败：发送频率超限，请稍后再试`，随后只能干等；群里表现为 bot 突然不说话。

**机制**：热群一小时几十条是正常的，`socialV2.send.maxSendPerHour` 撞线后每次发送都被 429。
如果 429 里**不带"还要等多久"**，模型会以为可以重试，于是连续重试全部失败，一个回合就卡在那里。

**现在的做法**：

- 429 带 `retryAfterMs` 和"请等待约 N 秒后再发；期间不要重试"，模型能自己退让；
- 限流按会话计数（`state/social-v2.json` 的 `sendTimes`），失败或未发出的消息会回滚预占额度，不产生"假 429"；
- 上限按群活跃度调（默认 8/分钟、60/小时；热群可到 120~360/小时）。

**注意**：调高上限后仍然频繁撞线，真问题通常不是限额而是**发言密度**——该调每轮条数与唤醒概率，而不是继续抬上限。

### 4.6 一个回合跑太久，把会话锁死

**指纹**：会话长时间处于"繁忙"，新的 @ 全被写成 `会话繁忙，暂存唤醒原因`；日志里同一回合的步数持续增长。

**机制**：模型可以在一轮里反复 `qq_wait_for_messages`（180~300 秒一次），只要它不主动收尾，回合就不结束；
而"会话繁忙"会让新消息只能排队。

**现在的做法**：`socialV2.turn.maxDurationMs`（默认 20 分钟）作为单回合预算。超预算后把 `wait` 钳到 15 秒，
并在返回里给出 `turnOverBudget` 与明确的收尾提示，迫使模型结束这一轮、把队列放出去。

## 五、系统提示语流进了聊天

**指纹**：对端收到「已停止」之类的系统话术；桥接日志同时出现回合被中止。

**根因**：回合被外部中止（用户点停止、或会话退役路径）时，桥接把提示语当成机器人发言发给了对方。

**处置**：中止提示只进日志 / 控制台，**不要进聊天**；同时在发起中止的路径上记录**触发来源**，否则无法回答"是谁停的"。

## 六、采集证据（只读，注意脱敏）

```bash
# 1) 链路健康（不输出密钥与聊天内容）
node ops/status.mjs

# 2) 各会话状态：未读水位、待发队列、唤醒配置
python3 - <<'PY'
import json, os
p = os.path.expanduser('qq-bridge/state/social-v2.json')
for k, c in json.load(open(p))['conversations'].items():
    print(k, '未读', len(c.get('unread') or []), '水位', c.get('lastUnreadSeq'),
          '待发', c.get('pendingWakeReasons'), '唤醒', (c.get('wakeConfig') or {}).get('mode'))
PY

# 3) 静默丢失计数（这三个数越大，§4.2 越严重）
grep -cE '跳过补发|会话繁忙|回合完成但无文本' qq-bridge/state/bridge.log

# 4) 回合是否根本没跑（看有没有 step/start）
#    会话文件是 zstd 压缩的 JSONL；解压后按 type 过滤 turn/start、step/start、turn/end
```

所有命令都只读；分享日志前请脱敏（账号、群号、昵称、聊天正文、令牌、本机路径）。

## 七、复盘清单（出现"不回复"时按序检查）

- [ ] `ops/status.mjs` 三项是否都 ok（网关 / DSH / 桥接）
- [ ] 会话事件里**有没有 `step/start`**（区分「模型没跑」和「跑了没说」）
- [ ] 活跃会话**是否被归档**（§2）
- [ ] 该会话是否稳定 400（§3，注意只有单个会话坏）
- [ ] 目标消息是否命中唤醒条件（§4.1，尤其称谓 / 代词 / 纯图片）
- [ ] `跳过补发` / `会话繁忙` 是否在涨（§4.2）
- [ ] 最后一条来信之后有没有 bot 的发送记录（§4.4，别被未读数误导）
- [ ] 聊天里是否出现系统话术（§5）
